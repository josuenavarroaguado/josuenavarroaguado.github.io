# 5. El problema que resuelvo / The problems I help solve

## ES

# Cuando la tecnología empieza a condicionar el crecimiento

El producto crece, pero cada cambio cuesta más.

La arquitectura acumula decisiones difíciles de revertir.

El equipo necesita más claridad, estándares y autonomía.

## EN

# When technology starts constraining growth

The product is growing, but every change is becoming more expensive.

Architecture has accumulated decisions that are increasingly hard to reverse.

Technical debt constantly competes with business priorities.

The engineering team needs clearer standards, stronger foundations, and more autonomy.

Cloud and infrastructure stop being an enabler and start creating friction.

Leadership wants to adopt AI, but there is still no clear strategy around use cases, architecture, security, providers, governance, or measurable value.

At that point, the answer is rarely another tool or a complete rewrite. What is needed is **technology judgment, clear priorities, and an executable evolution plan**.

# 10. Cómo trabajo / How I work

## ES

# Menos recomendaciones abstractas. Más decisiones ejecutables.

### 1. Entender el contexto

Empiezo por negocio, producto y equipo antes de entrar en tecnología: qué intenta conseguir la empresa, qué restricciones existen, qué decisiones ya se han tomado y dónde aparece la fricción.

### 2. Hacer visible el sistema

Arquitectura, plataforma, delivery, deuda técnica, dependencias, procesos y organización. El objetivo es crear una visión compartida del estado actual.

### 3. Priorizar

No todo problema técnico merece resolverse ahora. Distingo entre problemas reales, riesgos futuros y complejidad innecesaria para concentrar el esfuerzo donde tiene mayor impacto.

### 4. Definir una dirección

Principios, arquitectura objetivo, estándares, decisiones y roadmap. Suficiente estructura para alinear al equipo sin crear un proceso pesado.

### 5. Acompañar la ejecución

Cuando el engagement continúa, trabajo con los responsables internos para convertir la dirección acordada en decisiones, capacidades y cambios sostenibles.

**Principios de trabajo:**

- Contexto antes que herramientas
- Evolución antes que reescritura por defecto
- Simplicidad antes que arquitectura aspiracional
- Estándares antes que burocracia
- Equipos habilitados antes que dependencia externa
- IA cuando existe valor real
- Seguridad y gobernanza desde el diseño
- Decisiones explícitas y documentadas
- Arquitectura conectada con producto y negocio

## EN

# Less abstract advice. More executable decisions.

### 1. Understand the context

I start with business, product, and team context before going deep into technology: what the company is trying to achieve, which constraints exist, which decisions have already been made, and where friction is emerging.

### 2. Make the system visible

Architecture, platform, delivery, technical debt, dependencies, processes, and organization. The goal is to create a shared understanding of the current state.

### 3. Prioritize

Not every technical problem deserves to be solved now. I separate real problems, future risks, and unnecessary complexity so effort can be focused where it matters most.

### 4. Define direction

Principles, target architecture, standards, decisions, and roadmap. Enough structure to align the team without creating a heavy process.

### 5. Support execution

When the engagement continues, I work with internal leaders to turn the agreed direction into decisions, capabilities, and sustainable change.

**Working principles:**

- Context before tools
- Evolution before default rewrites
- Simplicity before aspirational architecture
- Standards before bureaucracy
- Enabled teams before external dependency
- AI where there is real value
- Security and governance by design
- Explicit, documented decisions
- Architecture connected to product and business
